# UAVSA-v1.0 架构设计

## 1. 设计目标

解决无人机算法「仿真 → 实机」迁移中的三个核心痛点：

1. **迁移难**：模型 / 传感器 / 控制接口不一致，导致算法迁移困难、重复调参严重。
2. **复现难**：开源算法复现门槛高，缺乏统一运行环境与标准化评测流程，横向对比困难。
3. **迭代慢**：缺乏自动化纠偏手段，人工分析日志、改参数、重跑周期长。

UAVSA-v1.0 用「双容器 + 大模型 Agent」构建一个可复用的标准化实验框架，
把「跑算法 → 看数据 → 改算法」的人工循环升级为 **Agent 自动闭环**。

### 职责划分

| 组件 | 位置 | 职责 |
|------|------|------|
| `sim_bridge` | docker1 | 控制 Gazebo/PX4 仿真，暴露运行指标（轨迹误差、收敛时间、碰撞等） |
| `agent` | docker1 | 自适应循环大脑：调用 LLM、编排工具、生成补丁、驱动重跑 |
| `algo_bridge` | docker2 | 对被测算法做标准化封装：build / run / patch / 状态查询 |
| `shared/` | 三方共享卷 | 算法源码、编译产物、结果日志、知识库文档 |

## 3. 通信与接口约定

三个服务之间通过 HTTP（FastAPI，OpenAPI 规范）通信，端口如下（容器内网）：

| 服务 | 端口 | 关键接口 |
|------|------|----------|
| `agent` | 8000 | `POST /session`（开始任务）、`WS /session/{id}/stream`（事件流） |
| `sim_bridge` | 8001 | `POST /scenario/start`、`GET /metrics`、`POST /scenario/stop` |
| `algo_bridge` | 8002 | `POST /build`、`POST /run`、`POST /patch`、`GET /status` |

> v1.0 的 ROS1 ↔ ROS2 桥接采用「桥接服务抽象」：`algo_bridge` 内部负责把
> `sim_bridge` 推送的传感器数据（里程计 / 点云）转为 EGO-Planner 需要的 ROS 话题，
> 再把规划轨迹回传给 `sim_bridge`。真实桥接实现见 `docker2/algo_bridge` 与文档
> `docs/02-quickstart.md` 的「ROS 桥接说明」。

## 4. Agent 自适应闭环（sim2real）

Agent 采用 **ReAct（推理-行动）** 范式，围绕「跑 → 看 → 改 → 重跑」循环：

```
用户给算法文件
      │
      ▼
 ① 封装封装：检索算法 → 注入 docker2 → 编译
      │
      ▼
 ② 仿真运行：sim_bridge 启动场景 → algo_bridge 运行算法
      │
      ▼
 ③ 采集评测：读取指标（跟踪误差/收敛/碰撞/能耗）+ 时序判别器打分
      │
      ▼
 ④ LLM 分析：结合指标 + RAG 知识库 → 定位问题 → 生成补丁
      │
      ├── 收敛 / 达上限 ──► ⑤ 生成评测报告
      │
      └── 继续 ──► 打补丁 → 重新编译 → 回到 ②
```

每次循环都会累积「运行记录 → 指标 → 分析 → 补丁」到会话记忆，供后续决策引用。

## 5. Agent 工具链

| 工具 | 类型 | 说明 |
|------|------|------|
| `search_algorithm` | 检索 | 在知识库中检索同类算法与配置（关键词 + 向量检索） |
| `retrieve_knowledge` | RAG | 从知识库文档中检索上下文片段，供 LLM 引用 |
| `run_simulation` / `stop_simulation` | 仿真控制 | 启停 Gazebo 场景、设置风场 / 障碍物 |
| `read_metrics` | 评测 | 读取标准化指标（跟踪误差、收敛时间、成功率等） |
| `run_algorithm` / `build_algorithm` | 算法控制 | 运行 / 编译 docker2 上的算法 |
| `patch_algorithm` | 纠偏 | 把 LLM 生成的代码补丁应用到算法并备份原文件 |
| `analyze_time_series` | 时序模型 | 对轨迹时序做异常 / 质量判别（对应 `Plan.md` 设想） |
| `generate_report` | 报告 | 汇总历次迭代，产出 Markdown 评测报告 |

## 6. 关键设计决策

1. **接口抽象而非紧耦合**：Agent 不直接操作 ROS，而是通过 `sim_bridge` / `algo_bridge` 两个
   薄封装服务交互，便于后续把 Gazebo 换成 Isaac Sim、把 EGO-Planner 换成其它算法。
2. **Mock 模式**：Agent 内置 Mock 后端（`agent/backends/mock.py`），无需 Docker 即可跑通完整
   闭环，用于演示、单测与算法封装逻辑的提前验证。
3. **知识库独立**：RAG 知识库放在 `shared/knowledge/`，支持随时增补文档、重新建索引。
4. **时序判别器即 tool**：把 `Plan.md` 中「时序自回归判别器」的设想落为一个可插拔 tool，
   在 v1.0 先以规则 + 轻量统计实现，预留模型加载接口。
